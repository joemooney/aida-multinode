- **Expected:** B reconciles (pull-rebase with structured union of `oplog.yaml`) or refuses with a clear next step; after following it, both nodes show all four changes (`TASK-811...-003`, edited `STORY-811...-001`, `TASK-8CF...-001`, edited `STORY-811...-002`) with no change lost.
- **Observed:**
  1. **Surprise 1 (`aida add` auto-pushes even when `auto_push = "manual"`):** When Node A ran `aida add`, it immediately pushed `TASK-811DEB6AAC5F4DC5B2C230E98E1463DB-003` to `origin/aida-store`. When Node B ran `aida add`, it committed `TASK-8CF8D5BD80B2434082EF9DFCCAA9FDD8-001` locally, tried to auto-push to `origin/aida-store`, got rejected, and automatically ran `pull_rebase_store_retry`.
  2. **FAIL 1 (`GIT_EDITOR=false` breaks `git rebase --continue` during `oplog.yaml` auto-merge):** Because both nodes appended to `oplog.yaml`, the rebase paused on a conflict in `oplog.yaml`. AIDA resolved `oplog.yaml` in-process and ran `git -c core.editor=true rebase --continue`. Because the Antigravity shell sets `GIT_EDITOR=false` in the environment (and Git gives `GIT_EDITOR` higher precedence than `-c core.editor=true`), `git rebase --continue` failed with:
     ```text
     Error: Pull failed: git rebase --continue failed without conflicts: error: There was a problem with the editor 'false'.
     Please supply the message using either -m or -F option.
     error: could not commit staged changes.
     ```
      Both `aida db sync --push` and `aida db sync --pull` on Node B failed with this exact error until `unset GIT_EDITOR` was run.
  3. **With `unset GIT_EDITOR`:** Node B's `aida db sync --push` automatically rebased (`auto-merged oplog: 11 operations after union`, `auto-merged oplog: 13 operations after union`, `Push complete after rebase.`). All 4 changes were preserved and verified on both nodes.
  4. **Surprise 2 (False-positive `Conflicts detected:` on Node A's fast-forward `aida db sync --pull`):** When Node A ran `aida db sync --pull` to pull Node B's changes, `aida db sync --pull` printed a false-positive conflict report for `STORY-811deb6aac5f4dc5b2c230e98e1463db-002` (which Node A had never edited!).
- **Timings:**
  - Node A `add` + `edit`: `8270 ms`
  - Node A `aida db sync --push`: `483 ms`
  - Node B failed `aida db sync --push` / `--pull` (with `GIT_EDITOR=false`): `1028 ms` / `775 ms`
  - Node B `aida db sync --push` (with `unset GIT_EDITOR`, including auto-rebase): `4555 ms`
  - Node A `aida db sync --pull`: `2133 ms`
- **Verdict:** **FAIL** (due to `GIT_EDITOR=false` overriding `-c core.editor=true` in `git_ops.rs:2254,2322` and false-positive conflict reporting in `git_backend_cmd.rs:1430`; data reconciliation itself succeeded with `unset GIT_EDITOR` and lost no changes).

### Issue 2 (S4a FAIL & S3 False Positive — P0): Asymmetric conflict handling, silent scalar loss on `aida db sync --push`, false-positive conflict alerts on fast-forward `aida db sync --pull`, and missing field-change history on `aida edit`

This failure has **four distinct interacting root causes** in `aida-core` and `aida-cli-lib`:

#### 2A. False-positive `Conflicts detected:` on clean fast-forward `aida db sync --pull` (S3)
- **Root Cause:**
  In `db_sync_local_window` (`/home/joe/ai/aida/aida-cli-lib/src/git_backend_cmd.rs` lines 1388–1433):
  1. Line 1388 snapshots all local requirements *before* pulling: `let local_reqs = ...`.
  2. Line 1395 runs `pull_rebase_auto_merge`.
  3. Line 1420 loads the store *after* pulling (`remote.requirements`) and calls `detect_store_conflicts(&local_reqs, &remote.requirements)`.
  4. Look at `detect_conflict(local, remote)` in `/home/joe/ai/aida/aida-core/src/conflict.rs` (lines 59–134):
     ```rust
     /// Returns None if there are no conflicts (versions are identical or one is strictly newer)
     pub fn detect_conflict(local: &Requirement, remote: &Requirement) -> Option<ConflictInfo> {
         if local.modified_at == remote.modified_at {
             return None;
         }
         // Immediately compares title, description, status, priority, owner, feature!
     ```
     Despite its doc comment ("or one is strictly newer"), `detect_conflict` **only checks `local.modified_at == remote.modified_at`** and never checks whether the pre-pull state was a strict ancestor of the post-pull state (i.e. a clean fast-forward where the local node made zero unpushed edits to that spec)! Therefore, whenever Node B edits any spec and pushes, Node A's next `aida db sync --pull` sees `pre_pull_req.modified_at != post_pull_req.modified_at` and falsely prints `Conflicts detected: ... Resolve with: aida edit <ID> ...`!
- **Proposed Fix:**
  - In `db_sync_local_window` (`/home/joe/ai/aida/aida-cli-lib/src/git_backend_cmd.rs:1388`), only run `detect_store_conflicts` when `pull_rebase_auto_merge` actually performed an `AutoMerged` rebase (or compare the **unpushed local commit range** `origin/<branch>..HEAD` before the pull against `origin/<branch>`, rather than comparing `pre_pull` vs `post_pull` on a fast-forward!). Specifically, if local `HEAD` before pull was an ancestor of `origin/<branch>` (fast-forward), local made no concurrent changes and `detect_store_conflicts` must not fire.

#### 2B. `merge_spec_upstream` drops non-colliding local scalar edits and `resolve_spec_conflict` hides scalar overwrites (S4a)
- **Root Cause:**
  1. During rebase (`rebase_auto_merge_onto` -> `resolve_spec_conflict` at `/home/joe/ai/aida/aida-core/src/git_ops.rs:2692–2766`), Git stage `:1:` is `base`, `:2:` (`ours` during rebase) is `upstream` (`origin/aida-store`), and `:3:` (`theirs` during rebase) is `local` (the local commit being replayed).
  2. `resolve_spec_conflict` calls `merge_spec_upstream(&base, &ours, &theirs)` (`/home/joe/ai/aida/aida-core/src/conflict.rs:428–457`):
     ```rust
     pub fn merge_spec_upstream(base: &Requirement, upstream: &Requirement, local: &Requirement) -> Requirement {
         let mut merged = upstream.clone();
         merged.history = union_history(&[&base.history, &upstream.history, &local.history]);
         ...
     ```
     Unlike `merge_spec_three_way` (`conflict.rs:254–365`), which uses `merge_scalar(&base.field, &ours.field, &theirs.field, ...)` so that a scalar field modified on **only one** side is preserved, `merge_spec_upstream` blindly clones `upstream` for **all** scalars! Even ifNode A only edited `title` and Node B only edited `description`, `merge_spec_upstream` discards Node B's `description` edit! And when both edited `title`, `merge_spec_upstream` overwrites `local.title` with `upstream.title`.

### Issue 5 (S7 Friction / Bug — P1): `aida mailbox send --to <user>` refuses with `unknown recipient` on work-node clones

- **Root Cause:**
  1.   2. When `aida mailbox send --to node-b` runs, `send_command` (`/home/joe/ai/aida/aida-cli-lib/src/mailbox_resolver.rs:351`) calls `PeopleCatalogView::load` (`/home/joe/ai/aida/aida-core/src/mailbox_identity.rs:150–320`), which populates known user handles only from:

     - `registry/nodes.toml` (`entry.user`)
     - `registry/roles.toml`
     - `registry/teams.toml`
     - existing `.aida-store/mailbox/<user>/` directories
     Because work-node clones do not write to `registry/nodes.toml`, even after Node B has created specs, added comments, and pushed commits to `origin/aida-store`, `PeopleCatalogView` has zero record of `node-b` unless `aida node team set-role` was manually executed!
  3. Furthermore, when `send_command` refuses (`mailbox_resolver.rs:373–394`), the error message says:

- **Proposed Fix:**
  1. **Improve recipient discovery or registration:** Either:

     - Update the refusal message in `aida-cli-lib/src/mailbox_resolver.rs:386–393` to explicitly tell the operator how to register a teammate handle in a work-node repo:
       `"register the user with 'aida node team set-role --role <role> <user>' or pass --broadcast"`.
  2. **Allow `aida node team set-role` to work non-interactively:** Currently `set-role` requires an interactive terminal (`stdin` TTY) for the lease-holder gate. Supporting a non-interactive flag (or allowing initial bootstrap when `roles.toml` is empty) removes the scripting barrier.
